# Ursula 0.3.0 vs 0.4.0 under the Workflow World workload

Date: 2026-07-28

## Verdict

Ursula 0.4.0 is a large storage-efficiency and indexing release. The first integrated test indexed the source 2.26× as fast, halved durable index parts, reduced index query p99 by 48.4%, and reduced current server and index S3 objects by more than 80%, but showed 8.5% lower median Workflow throughput and 10.0% higher run p99 while both indexer replicas shared three 2-vCPU voter nodes.

Controlled same-version ablations reproduced the regression only under co-located indexing. Moving the two stateless indexers to a dedicated two-node ARM pool restored median Workflow throughput to 650.1 steps/s and run p99 to 37.307 s, respectively 1.0% better and 1.3% lower than the 0.3.0 baseline. The regression was therefore a deployment-topology defect: the new faster indexer competed with Raft runtime cores on undersized voter nodes, not a foreground server hot-path regression.

## Regression investigation and resolution

The `0.4.0-beta.1` binary used for the ablation contains the same Ursula code as the benchmarked 0.4.0 commit; subsequent commits only added release metadata and benchmark publishing. Each diagnostic deployment used fresh storage, index, and Workflow bucket prefixes on three fresh `m7g.large` voter nodes.

| 0.4.0-beta.1 topology | Workflow steps/s | Run p99 | Index durable time | Durable parts |
| --- | ---: | ---: | ---: | ---: |
| Indexers idle, median of three | 639.8 | 37.649 s | N/A | N/A |
| Two full-speed indexers co-located with voters, one reproduced sample | 564.9 | 43.144 s | 61.269 s | 10 |
| Two full-speed indexers on a dedicated ARM pool, median of three | **650.1** | **37.307 s** | 68.446 s | 9 |
| Ursula 0.3.0 original mixed baseline, median of three | 643.7 | 37.795 s | 106.000 s | 20 |

The dedicated-pool Workflow samples were 618.5, 650.1, and 652.7 steps/s with run p99 values of 39.143 s, 37.307 s, and 36.946 s. Corresponding index durable times were 76.927 s, 65.337 s, and 68.446 s with 33, 6, and 9 durable parts. The first sample included cold convergence; medians are reported without discarding it.

The production-shaped canary fix uses two on-demand `m7g.medium` ARM nodes, one indexer replica per availability zone. The nodes are tainted so voters and gateways cannot schedule there. Cloud GitOps PRs [#50](https://github.com/tonbo-io/cloud/pull/50), [#51](https://github.com/tonbo-io/cloud/pull/51), and [#52](https://github.com/tonbo-io/cloud/pull/52) provisioned the pool, handled the beta chart's merged selector default, and made zone separation mandatory. The canary converged `Synced/Healthy` with both indexers Ready on distinct nodes and no voter restart.

## Workload

Each version received one excluded warm-up and three formal samples. Every formal sample ran these two loads concurrently:

1. Complete Workflow capacity: 500 runs × 50 sequential steps = 25,000 logical steps, eight queue shards, one iteration.
2. Event-time indexing: create one `application/json` source stream, append 100,001 records as 400 × 250-record batches with 100 ms spacing, wait for `durable_through_record = 100001`, then execute 100 event-time queries.

The same application tier, benchmark image, Ursula node instances, resource requests, Raft group count, runtime core count, S3 bucket, and client scripts were reused. Ursula 0.4.0 used its supported `PreferSameZone` gateway Service behavior; this is part of the version being evaluated rather than a backport into 0.3.0.

## S3 object shape

The prefixes were fresh and received the same four Workflow jobs and four indexed source streams: three 100,001-record formal streams plus one 101-record smoke stream. The comparison below uses the follow-up inventory taken at approximately the same 22-minute deployment age.

| Current objects | Ursula 0.3.0 | Ursula 0.4.0 | 0.4.0 change |
| --- | ---: | ---: | ---: |
| Server storage plane | 6,298 | 1,056 | **-83.2%** |
| Index plane | 2,243 | 330 | **-85.3%** |
| Combined | 8,541 | 1,386 | **-83.8%** |

| Current bytes | Ursula 0.3.0 | Ursula 0.4.0 | 0.4.0 change |
| --- | ---: | ---: | ---: |
| Server storage plane | 112.03 MB | 43.18 MB | **-61.5%** |
| Index plane | 15.59 MB | 3.52 MB | **-77.4%** |

The representation changed qualitatively. Ursula 0.3.0 left 4,135 stream chunk objects plus 2,106 per-stream cold-index objects. Ursula 0.4.0 represented the same loaded data as three shared packed objects totaling 25.12 MB; its largest pack was 8.38 MB. The remaining 1,053 server objects were Raft snapshot objects and per-node references rather than tiny stream chunks. The index plane reduced current Parquet parts from 688 to 106 and layout objects from 688 to 106.

S3 version inventory showed the same direction: 8,327 server versions and 3,205 index versions on 0.3.0 versus 1,056 server versions and 540 index versions on 0.4.0 at the same approximate age. This validates a large reduction in visible S3 version churn, but it is not a complete request-billing calculation because failed conditional writes, reads, LIST operations, and lifecycle charges are not represented by version inventory.

## Compute and network signals

The three Ursula nodes were not CPU saturated. Coarse five-minute EC2 telemetry averaged approximately 20.0% CPU across the three nodes in the main 0.3.0 window and approximately 17.5% in the 0.4.0 window. This makes simple CPU exhaustion an unlikely explanation for the Workflow regression.

The same coarse EC2 telemetry showed approximately 29% less aggregate node network input plus output in the corresponding loaded five-minute bins on 0.4.0. This is directionally consistent with compressed replication payloads, shared channels, rolling append streams, finite response compression, and same-zone gateway routing added after 0.3.0. It is not an exact cross-AZ billing result: the benchmark packet meter was not reset around this A/B, and EC2 `NetworkIn`/`NetworkOut` includes same-zone and unrelated node traffic.

Ursula 0.4.0's new counters reported approximately 91.8–92.1 MB of replication request payload per 25,000-step Workflow sample, a 98.2%–99.8% gateway leader-cache hit rate after warm-up, and only 3–31 redirects per sample. Ursula 0.3.0 did not expose the same counters, so these numbers prove the 0.4.0 path is operating as designed but cannot provide an exact version-to-version byte ratio.

## What improved between 0.3.0 and 0.4.0

The measured changes align with the main implementation work after 0.3.0:

- Index lifecycle fixes bound object growth, prevent higher-level compaction starvation, and reduce S3 object churn.
- Cold storage compacts small chunks toward target-sized objects and packs small objects across streams by Raft group.
- Raft snapshots use shared compressed content-addressed objects and amortized scheduling.
- Replication payloads are compressed; peer channels are shared; Append traffic is multiplexed and frame-batched while keeping per-group consensus.
- Gateway leader routing is cached, h2c upstreams are multiplexed, finite record responses are compressed, and Helm can prefer same-zone endpoints.

The S3 and index improvements are large enough to treat those parts of 0.4.0 as validated. The original co-located result does not validate a foreground improvement, while the dedicated-pool ablation removes the observed regression and slightly exceeds the 0.3.0 Workflow baseline.

## Next steps

1. Repeat the dedicated-pool comparison against PostgreSQL with exact source-side cross-AZ packet metering reset around every sample.
2. Capture per-container CPU and throttling through kubelet summary metrics or Container Insights so the extra two indexer nodes can be converted into cost per million indexed records and Workflow steps.
3. Keep the 0.4.0 object layout and dedicated indexer scheduling. Do not trade the measured 83.8% combined current-object reduction back for co-location that regresses foreground latency.
